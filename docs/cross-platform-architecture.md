# Cross-Platform Architecture

Date: 2026-07-10

## Existing Stack

- Frontend: React 18, TypeScript, Vite, Tailwind CSS, lucide-react.
- Backend: Azure Functions Node v4 with Azure Table Storage through `@azure/data-tables`.
- Authentication: Azure Function bearer token API with server-side Super Admin checks.
- Deployment: Hostinger serves static web/PWA assets from `dist`; Azure hosts API, auth, tracking sync, notifications, and webhooks.
- Desktop: Tauri 2 wraps the same Vite frontend; Windows targets are MSI and NSIS setup.exe.
- Data integrations: Excel tracking importer and tracking API live in `api/src/lib/tracking`.

## Shared Frontend Strategy

The same `src/` application runs as the hosted web app, installable PWA, and Tauri desktop webview. Business rules stay in shared frontend/backend modules; there is no separate Windows-specific copy of dashboard logic.

## PWA Strategy

- `public/manifest.webmanifest` defines stable app identity, icons, scope, theme, and standalone display.
- `public/service-worker.js` caches static assets and offline fallback only.
- API, auth, credential, and non-GET requests are excluded from cache.
- `src/pwa/registerServiceWorker.ts` emits the update event shown as `New version available — Update now`.
- `src/pwa/installPrompt.ts` handles supported browser install prompts; iOS/iPadOS is documented as Share -> Add to Home Screen.

## Windows Packaging Strategy

- `src-tauri/tauri.conf.json` builds the same frontend into Tauri 2.
- `src-tauri/src/main.rs` registers native notification, single-instance, autostart, and tray/focus behavior.
- `src-tauri/Cargo.toml` enables tray icons and notification/autostart plugins.
- MSI and NSIS setup.exe outputs are generated by `npm run desktop:build` when Rust/Cargo and Windows build prerequisites are present.

## Notification Delivery Strategy

- User devices register through `/api/devices/register` or `/api/push/subscribe`.
- Logout revokes the current device through `/api/push/unsubscribe`.
- In-app inbox is authoritative and works without OS notification permission.
- PWA Web Push uses VAPID keys from Azure settings; only `VITE_VAPID_PUBLIC_KEY` reaches the frontend.
- Tauri Level 1 desktop notifications use controlled inbox polling while the app is running or in tray, then display native Windows notifications through the Tauri notification plugin.
- Delivery records distinguish queued, provider accepted, failed, blocked, and revoked states. Provider accepted is not treated as a read receipt.

## Database / Storage

Azure Tables are created lazily by backend code:

- `FmsUserDevices`
- `FmsNotificationPreferences`
- `FmsNotificationInbox`
- `FmsNotificationDeliveries`
- `FmsWhatsAppConsents`
- `FmsNotificationRules`
- `FmsNotificationTemplates`

No browser, service worker, or installer contains provider secrets.

## Security Model

- Backend resolves recipients from authenticated users and server-side criteria.
- Super Admin endpoints enforce role authorization on the server.
- Device/subscription records are linked to the authenticated user, not phone numbers.
- Duplicate push endpoints are detached from older users/devices before being attached to the current login.
- Push payloads include only short summary fields and sanitized metadata.
- WhatsApp requires explicit consent and separate Meta credentials.

## Platform Limitations

- iOS/iPadOS PWA installation is manual through Share -> Add to Home Screen.
- Browser push requires explicit user permission and a configured VAPID key pair.
- Tauri native notifications work for the installed app; development notifications can show a generic shell name.
- Windows terminated-app push is Level 2 and requires Microsoft/Azure registration described in `docs/windows-wns.md`.
- Local installer generation is blocked until Rust/Cargo and Windows build prerequisites are installed on the build machine.
